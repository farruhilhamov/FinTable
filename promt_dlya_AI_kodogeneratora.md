Ты — опытный full-stack разработчик. Напиши веб-приложение для личного финансового учёта на Python (Django) с фронтендом на Django templates + HTMX/Alpine.js (или React, если считаешь это оправданным для данного проекта) и БД PostgreSQL (с возможностью локального запуска на SQLite).

## Контекст и цель
Приложение — персональный/мультипользовательский трекер финансов. Каждый пользователь ведёт учёт своих счетов, вкладов, доли в компании (аналог ценных бумаг), доходов и расходов; сервис автоматически считает прибыль/убыток (P&L) и общий капитал (Net Worth), строит статистику и поддерживает импорт/экспорт данных через единую БД. Валюта — узбекский сум (UZS), мультивалютность не нужна.

## Модели данных (реализуй как Django-модели с миграциями)

1. **User** — стандартная модель Django (email как логин).
2. **Account** — счёт хранения денег: name, type (card/cash/other), user (FK), с расчётным текущим балансом на основе связанных транзакций.
3. **Category** — категория дохода/расхода: name, type (income/expense), user (FK, nullable для системных дефолтных категорий), is_default, is_active.
   При создании пользователя автоматически создать копии дефолтных категорий:
   - Расходы: Еда и продукты, Кафе и рестораны, Транспорт, Жильё и коммунальные услуги, Здоровье и медицина, Одежда, Развлечения и прогулки, Связь и интернет, Образование, Подарки, Путешествия, Прочие расходы.
   - Доходы: Зарплата, Премия/бонус, Пополнение, Доход от вклада, Доход от доли/ценных бумаг, Прочие доходы.
   Пользователь должен иметь возможность создавать свои категории, редактировать и архивировать (не удалять физически, чтобы не терять историю).
4. **Transaction** — операция: user (FK), account (FK), category (FK), amount (Decimal, UZS), type (income/expense), date, description.
5. **Deposit** — вклад: user (FK), name, account (FK, nullable), principal_amount (Decimal), annual_rate (Decimal, % годовых), start_date, capitalization_type (choices: simple / monthly_compound), status (active/closed), closed_date (nullable).
   Реализуй метод/property `get_accrued_income(as_of_date=None)`, который считает накопленный доход:
   - simple: `principal * (annual_rate/100) * days_elapsed / 365`
   - monthly_compound: `principal * (1 + annual_rate/100/12) ** months_elapsed - principal`
   Также верни текущий баланс вклада = principal + accrued_income.
6. **Security** — доля/ценная бумага: user (FK), name, acquisition_value (Decimal, UZS), quantity_or_share (опционально).
7. **SecurityValuation** — история переоценок: security (FK), value (Decimal), date. Текущая стоимость = последняя запись по дате. P&L по бумаге = текущая оценка − acquisition_value (или сумма изменений между переоценками за период).
8. **RecurringTemplate** (опционально, но реализуй) — шаблон регулярной операции: user, category, account, amount, type, day_of_month, description, is_active. Добавь management-команду или scheduled task (Celery beat или простой cron-скрипт), которая в указанный день месяца создаёт Transaction на основе активных шаблонов.

## Ключевая бизнес-логика

**Расчёт P&L за период** (сумма трёх компонентов):
1. Доходы по транзакциям минус расходы по транзакциям за период.
2. Сумма накопленного дохода по всем активным вкладам, приходящегося на период (разница accrued_income на конец и начало периода).
3. Изменение стоимости всех Security за период (по SecurityValuation).

**Net Worth (общий капитал) на дату** = сумма балансов всех Account + сумма текущих балансов всех активных Deposit (principal + accrued_income) + сумма текущих оценок всех Security.

Реализуй сервис-слой (например `services/analytics.py`) с функциями `calculate_pnl(user, date_from, date_to)` и `calculate_net_worth(user, as_of_date=None)`, использующими агрегирующие ORM-запросы (`annotate`, `aggregate`), а не построчные Python-циклы, для производительности при больших объёмах данных.

## Веб-интерфейс (страницы/формы)

- Регистрация / вход / выход (Django auth).
- Dashboard: карточки с Net Worth, P&L за текущий месяц, график динамики капитала по месяцам (Chart.js), последние транзакции.
- Страница "Транзакции": таблица с фильтрами по датам/категории/счёту, форма добавления/редактирования/удаления.
- Страница "Счета": список счетов с балансами, форма добавления/редактирования.
- Страница "Вклады": список вкладов с принципалом, ставкой, накопленным доходом (обновляется динамически на текущую дату), форма добавления/закрытия вклада.
- Страница "Ценные бумаги / Доли": список с текущей оценкой и P&L, форма добавления переоценки.
- Страница "Категории": управление пользовательскими категориями (создание/редактирование/архивация), отдельно отображаются системные дефолтные.
- Страница "Статистика": фильтр периода, диаграммы доходов/расходов по категориям (pie/bar через Chart.js), таблица доходы/расходы по месяцам за последние 12 месяцев.
- Страница "Импорт/экспорт": кнопки экспорта каждой сущности в CSV, кнопка полного экспорта БД (ZIP с CSV-файлами по каждой модели), форма загрузки CSV для импорта с валидацией и построчным отчётом об ошибках.

## Требования к безопасности и изоляции данных

- Строго фильтруй все QuerySet по `request.user` через миксин/декоратор (например `LoginRequiredMixin` + переопределение `get_queryset` во всех views), чтобы пользователь не мог получить доступ к чужим данным даже через прямой запрос по ID.
- Пароли — только через Django встроенный хешинг.
- Используй CSRF-защиту Django по умолчанию (не отключай).
- Для продакшн-конфигурации добавь настройки для HTTPS (`SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`).

## Импорт/экспорт — формат

Экспорт каждой модели в CSV со всеми полями (кроме `id` пользователя — фильтруется автоматически по текущему пользователю), с человекочитаемыми заголовками колонок. Задокументируй формат в README: названия колонок, обязательность, типы данных, формат даты (ISO 8601). Импорт должен: (1) валидировать структуру CSV перед применением, (2) обрабатывать построчно с накоплением списка ошибок (не прерывать весь импорт из-за одной плохой строки), (3) поддерживать upsert-логику там, где это применимо (например, категории — не дублировать при повторном импорте).

## Структура проекта и качество кода

- Стандартная структура Django-проекта с отдельными приложениями: `accounts` (пользователи/auth), `finance` (Account, Transaction, Category), `deposits` (Deposit), `securities` (Security, SecurityValuation), `analytics` (сервисы расчёта P&L и Net Worth), `importexport` (импорт/экспорт CSV).
- Напиши unit-тесты минимум для: расчёта накопленного дохода по вкладу (simple и compound), расчёта P&L, изоляции данных между двумя пользователями (тест должен проверить, что пользователь A не может получить данные пользователя B).
- Добавь `requirements.txt`, инструкцию по запуску (`README.md`) — установка зависимостей, миграции, создание суперпользователя, запуск dev-сервера.
- Используй Decimal (не float) для всех денежных полей во избежание ошибок округления.
